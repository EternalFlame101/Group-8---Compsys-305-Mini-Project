## 1. Project Brief vs. What We Actually Built

### What the spec asked for
The project brief specified a **Flappy Bird** clone: a side-scrolling game where a bird navigates between pipe obstacles, controlled by a PS/2 mouse, displayed on a 640×480 VGA screen at 60 Hz on an Intel Altera DE0-CV FPGA board. The spec permitted groups to modify the game concept to make it "more interesting and challenging" — the primary requirements were: two game modes (Training and Single Player), obstacles and gifts, increasing difficulty levels, a proper start/end UI, score and time displays, pause/resume, and LFSR-based random obstacle generation.

### What we built instead — and why
We designed a **3D perspective endless runner** — a significantly more ambitious reinterpretation of the brief. Rather than a flat side-scroller, our game uses a first-person perspective track receding into the horizon, with three lanes the player can shift between. The player character is a cat ("Jasper") that runs toward the screen. This decision was made to:
1. Demonstrate a more advanced understanding of hardware graphics (perspective projection in VHDL).
2. Make the game more visually distinguishable and impressive to assess.
3. Justify deeper use of hardware resources like DSP blocks and block RAM.

The core spec requirements are all met: two modes, obstacles and gifts, three difficulty levels tied to score, start/end screens with mouse navigation, score/lives/time HUD, pause/resume, and LFSR-based spawning.

## 4. Clock Domains

Two independent clock domains operate simultaneously:

### CLOCK_50 (50 MHz)
- Drives: SD card (SPI), Keyboard, Mouse, Audio_Playback, Game_Timer, jukebox process, startup reset counter.
- Period: 20 ns. Achieved setup slack: **11.229 ns** → maximum achievable frequency: ~**114 MHz**.

### video_clock / Pixel Clock (25 MHz)
- Generated by `Video_PLL` (Quartus PLL IP) from CLOCK_50 via a 2× frequency divider.
- Drives: VGA_Sync, all display pipeline modules, Player, Moving_Object × 3, Game_Master FSM, Spawn_Control.
- Period: 40 ns. Achieved setup slack: **24.468 ns** → maximum achievable frequency: ~**64 MHz**.
- Distributed via GLOBAL buffer primitive to handle ~1000 load fanout without clock skew.

### Cross-Domain Signal Handling
Signals crossing from CLOCK_50 into the video_clock domain (keyboard/mouse inputs, SD card status) pass through **2-flip-flop metastability synchronizers** — required to prevent Quartus from timing the entire PS/2 decode chain as one combinational path into the video pipeline (which would collapse the achievable pixel clock to ~46 MHz).

A **335 ms startup hold counter** (24-bit counter at 50 MHz) keeps all game logic in reset until the PLL achieves lock.

## 5. Display Pipeline (Layered Rendering)

All display modules are driven by the same `pixel_row` / `pixel_column` coordinates from `VGA_Sync`, and produce RGB outputs. The `Screen_Compositor` selects the final pixel from the appropriate layer at each clock cycle.

### VGA_Sync
Standard 640×480 @ 60 Hz timing. Horizontal: 800 total clocks (640 active + 160 blanking), sync pulse at clocks 659–755. Vertical: 525 total rows (480 active + 45 blanking), sync at rows 493–494. Outputs: `pixel_row`, `pixel_column`, `hsync`, `vsync`, gates RGB to black during blanking.

### Rendering Layers (bottom to top)

**Layer 1 — Background_Generator**
- Rows 0–319: Sky. Reads from `Background_ROM` (altsyncram M9K block). ROM is 12,800 entries covering a 64×200 logical image, downsampled 4:1 to fill 640×320 screen pixels. ROM address = `(row/4) × 160 + (col/4)`.
- Rows 320–479: Ground. Procedural XOR dither pattern on row/column bits — avoids needing a ground ROM.
- Output registered (single-cycle ROM read latency absorbed).

**Layer 2 — Track_Generator**
- Renders the three-lane road surface with converging perspective lane dividers.
- Uses `Perspective_ROM` (same altsyncram instance also used by Moving_Object) to look up lane spread at each row depth.
- Lane divider positions shift horizontally based on `cat_view_position` (player's lateral offset, range −64 to +64 pixels) — this gives the steering illusion as the player moves between lanes.

**Layer 3 — Moving_Object × 3 (one per lane)**
The most complex display module. Each instance renders a single approaching object in 3D perspective. See Section 8 for full detail.

**Layer 4 — Player (Sprite Renderer)**
Renders the cat character sprite. 24 separate sprite ROMs (altsyncram M9K blocks loaded from `.mif` files) covering all animation states. See Section 7 for full detail.

**Layer 5 — Object_Manager / Player_And_Objects_Manager**
Composites the player sprite over the correct obstacle sprite (selects which of the 3 lane objects the player is in front of/behind based on current lane and depth).

**Layer 6 — Graphics_Manager**
Combines background layer with the composited sprites into the final game pixel.

**Layer 7 — HUD_Overlay**
Draws LIVES / SCORE / TIME text using `Character_ROM` (6×8 pixel font). Text rendered at SCALE 2 for labels, SCALE 4 for digits. Score decoded from 10-bit binary to 3 BCD digits via combinational priority chain. Leading zeros blanked to spaces. A pipeline register breaks the 21 ns BCD-decode → character-lookup path into two ≤12 ns stages.

**Layer 8 — Start_Screen / End_Screen**
Overlay screens for menus. See Section 10.

**Final — Screen_Compositor**
Priority mux selecting final pixel:
1. Start screen active → mouse cursor > start screen text/sprite > black
2. End screen active → mouse cursor > win/lose text > black
3. Paused → pause text > HUD > game pixel
4. Normal gameplay → HUD (if non-black) > game pixel

Input and output pipeline registers inserted purely to break timing paths (one ~24 ns path split into 2× ~12 ns stages).

## 6. Game Logic FSM — Game_Master.vhd

Central finite state machine. Runs on `video_clock` domain.

### States

```
         ┌──────────────────────────────────────────────────────────┐
         │                       INIT_SCREEN                        │
         │  startscreen_fsm='1', game_enable='0'                    │
         │  Waits: start screen confirmed active AND mode selected   │
         └─────────────────┬──────────────────────────┬────────────┘
                           │ mode='0'                 │ mode='1'
                           ▼                          ▼
                    ┌──────────┐              ┌──────────────┐
                    │ TRAINING │              │    NORMAL    │
                    │ 3 lives  │              │   1 life     │
                    │ win@10   │              │   win@30     │
                    └────┬─────┘              └──────┬───────┘
                         │ pause_input               │ pause_input
                         ▼                          ▼
                    ┌──────────────────────────────────┐
                    │              PAUSE               │
                    │    game_enable='0'               │
                    │    prev_state latched            │
                    └──────────────────────────────────┘
                         │ pause_input again
                         ▼ (returns to prev_state)
                    ┌──────────┐              ┌──────────────┐
                    │   WIN    │              │     LOSE     │
                    │ score    │              │ lives = 0    │
                    │ threshold│              │              │
                    └────┬─────┘              └──────┬───────┘
                         └──────────┬───────────────┘
                                    │ endscreen acknowledged
                                    ▼
                              INIT_SCREEN
```

### Speed Escalation (Combinational on Score)
Controls `speed_select` (2-bit), consumed by `Moving_Object` to set advance rate:

| Condition | speed_select | Approx. wave period |
|---|---|---|
| game_enable = '0' (paused/menu) | "00" | freeze |
| Training mode, or score < 10 | "01" | ~5.3 s/wave |
| Score 10–19 | "10" | ~3.5 s/wave |
| Score ≥ 20 | "11" | ~2.6 s/wave |

### Lives System
Internal 2-bit counter counts **up** toward "11" (display is inverted: "11" = 0 lives).
- Training start: internal_lives ← "00" (shows 3 lives)
- Normal start: internal_lives ← "10" (shows 1 life)
- On collision (guarded): internal_lives ← internal_lives + 1
- `god_mode` input (SW[2]) blocks the increment

**Collision Guard:** Arms 1 clock after `game_enable` goes high (first clean frame). Re-arms only after `object_collision` goes low — prevents multiple life deductions from a single sustained collision.

### Scoring
- Gifts (type "001"): +1 point on `gift_collision` rising edge (only while grounded)
- Wave arrivals: +1 point when any lane's object reaches bottom (`arrived_0/1/2`); `wave_scored` latch prevents double-counting
- Win conditions: score ≥ 10 (Training), score ≥ 30 (Normal), or score = 999 if `SW[2]` dev mode active

## 7. Player — Player.vhd

Handles the cat sprite rendering and all three movement systems simultaneously.

### Animation System (24 Sprite ROMs)
Each animation frame is a separate `Sprites_Display` instance wrapping its own `Sprites_ROM` (altsyncram M9K block loaded from `.mif` file):
- **Idle/Neutral:** 1 frame
- **Walk cycle:** 5 frames (neutral → right_1 → right_2 → right_1 → neutral → left_1 → left_2 → left_1, cycling)
- **Jump:** 8 frames (non-linear sequence for visual interest)
- **Dive/Squish:** 6 frames (squish down and back up)
- **Roll (lane transition):** 8 frames at 8 rotation angles (−45°, −90°, −135°, −180°, −225°, −270°, −315°, 0°) — reversed for opposite direction

**Frame priority mux (highest wins):**
1. `transition_active = '1'` → show roll frame
2. `dive_active = '1'` → show squish frame
3. `current_state = '1'` (jumping) → show jump frame
4. Default → show walk cycle frame

### Lane Shifting
- `view_pos_int`: signed pixel offset, −64 (left lane) to +64 (right lane)
- Advances 2 pixels per vsync (TRANSITION_SPEED), over 64 frames (LANE_TRANSITION_FRAMES) ≈ 1 second per lane
- Lane number (0/1/2) determined by crossing ±32 thresholds
- Holding the key continuously chains new transitions seamlessly
- Pressing opposite direction mid-transition reverses direction and mirrors roll_frame_index
- Roll animation plays only during active transition

### Jump — Jump_Offset_LUT.vhd
Precomputed parabolic lookup table. 65 entries indexed by `jump_frame_count` (0–64).

**Formula:** `offset(f) = PEAK_HEIGHT − (PEAK_HEIGHT × d(f)²) / TOTAL_FRAMES²`  
where `d(f) = |TOTAL_FRAMES − 2f|`

This replaced a runtime multiply+divide that was the critical timing path limiting the design to ~45 MHz. With the LUT: ROM access (~10 ns) + register = one clean pipeline stage, enabling 64 MHz target.

Peak height ≈ 60 pixels. Jump duration: 64 vsyncs ≈ ~1.07 seconds.

### Dive and Fast-Drop
- Normal dive: 32-frame squish animation (8 frames × 4 hold), only activates when grounded
- Dive mid-jump: `jump_frame_count` snaps to `TOTAL_FRAMES − 10` → cat lands in ~10 vsyncs (~167 ms) regardless of current height. Squish animation plays in parallel.

### Cross-Domain Synchronization (Critical)
Keyboard and mouse inputs arrive on CLOCK_50. Player.vhd inserts 2-FF synchronizers on all four inputs (`shift_left_input_meta` → `shift_left_input_sync`, etc.) before they enter the video_clock domain. Without this, Quartus times the full PS/2 decode → synchronizer → Player combinational path, collapsing the achievable pixel clock to ~46 MHz.

## 8. Moving_Object — Moving_Object.vhd (Per Lane × 3)

The most algorithmically complex module. Renders approaching obstacles/gifts with real 3D frustum geometry, all in hardware.

### Distance and Speed Management
- `object_distance`: 8-bit counter, 0–159 (depth index into Object_ROM)
- Advances per vsync at a rate set by `speed_select`
- **Fractional stepping** to simulate visual acceleration (objects appear to speed up as they approach):

| Zone (distance) | Advance per vsync | Average step |
|---|---|---|
| 0–31 | always 1 | 1.00 |
| 32–63 | +2 once every 4 frames | 1.25 |
| 64–95 | alternates 1/2 | 1.50 |
| 96–127 | +1 once every 4 frames | 1.75 |
| 128–159 | always 2 | 2.00 |

Object "arrives" (triggers Spawn_Control) when `object_distance ≥ 159`.

### Object Geometry — Object_ROM.vhd
160-entry altsyncram lookup (80-bit output, indexed by distance 0–159).
Precomputed at synthesis time, stored in M9K blocks:

| Field | Bits | Description |
|---|---|---|
| obj_sd | [79:70] | Back-face depth scaling factor |
| obj_y | [69:60] | Vertical center position on screen |
| obj_h | [59:50] | Front face height |
| obj_w | [49:40] | Front face width |
| obj_wb | [39:30] | Back edge width |
| top_h | [29:20] | Top face height |
| top_taper | [19:10] | Frustum convergence rate (top) |
| side_taper | [9:0] | Side wall convergence rate |

### Perspective Scaling — Perspective_ROM.vhd
Separate altsyncram, converts track distance to horizontal lane spread. Determines how far apart the lane positions are at each depth. Same ROM instance shared between Moving_Object and Track_Generator.

### 3D Frustum Rendering
Each object renders three visible faces:
1. **Front face:** Bottom of the frustum — the full-width face facing the player. Height/width from Object_ROM.
2. **Top face:** Sits above front face. Left and right edges converge inward toward the horizon using `top_taper`. Skew direction varies with player's lateral position (`cat_view_position`) — looks correct from any viewing angle.
3. **Side faces:** Walls connecting top to front edge. Converge with distance using `side_taper`.

**Rendering priority:** Front > Top > Side (front pixels occlude faces behind).

### Object Type Colors
| Type (3-bit) | Meaning | Color |
|---|---|---|
| "000" | Empty | Black (invisible) |
| "001" | Gift | Yellow (R+G high) |
| "010" | Small obstacle (ground) | Green |
| "011" | Large obstacle (ground) | Blue |
| "100" | Airborne hazard | Red |

### Overflow/Underflow Protection
All boundary computations done in 12-bit arithmetic. Bit 11 acts as sign (underflow flag). Underflow and overflow flags are ORed into boundary comparisons to gate off rendering when object is partially off-screen — prevents faces from wrapping across the full screen width.

### Pipeline Architecture
Heavily pipelined to hit >100 MHz timing target:
- **Frame_Stage_1 (combinational):** Lane offset, perspective distance calculations
- **Frame_Stage_2 (registered, vsync-stable):** Width/height products, taper precomputes
- **Per-Pixel Stage 1A/1B/1C (registered):** Row/column boundary derivations
- **Per-Pixel Stage 2 (combinational + output register):** Comparisons, color mux

## 9. Collision Detection — Collision_Detector.vhd

Pure combinational logic — no registers. Checks per lane simultaneously.

### Collision Rules
```
Row threshold: obj_row >= 140 (empirical — below this, object visually hasn't reached player)

Gift collision (type "001"):
  → same lane AND player grounded (player_state='0') AND row >= 140

Small obstacle (type "010"):
  → same lane AND player grounded AND row >= 140

Large obstacle (type "011"):
  → same lane AND row >= 140 (always collides — must dodge by lane change)

Airborne hazard (type "100"):
  → same lane AND player NOT diving (player_dive='0') AND row >= 140
```

Lane matching: `player_lane` (0/1/2 from Player.vhd) compared against which lane instance triggered.

Outputs three pairs: `lane_X_gift_collision` and `lane_X_object_collision`, consumed by Game_Master.

## 10. Obstacle Spawning — Spawn_Control.vhd + Wave_ROM.vhd + LFSR

### LFSR (Linear Feedback Shift Register)
8-bit Galois LFSR, seed `0xB1` ("10110001"). Standard polynomial taps. Generates pseudo-random 8-bit values. Advances once per wave arrival (when `arrived_0/1/2` pulse fires). Same seed every reset → deterministic/repeatable sequence.

### Wave_ROM.vhd
256-entry altsyncram (9-bit output, indexed by LFSR output).  
Output format: `[lane_0_type(2:0), lane_1_type(2:0), lane_2_type(2:0)]`  
Each entry specifies the 3-bit object type for each of the three lanes for that wave.  
Populated at synthesis from `.mif` file.

### Spawn_Control FSM (4 States)
1. **IDLE:** Wait for `arrived_0/1/2` pulse.
2. **PULSE:** Assert `lfsr_enable='1'` → LFSR advances one step.
3. **ROM_SETTLE:** Wait 1 cycle for ROM address register to settle.
4. **LATCH:** ROM output valid. Latch `lane_X_type` outputs. If all three lanes output "000" (empty wave), loop back to PULSE immediately — skips invisible waves to avoid dead time.

## 11. Input Handling

### Keyboard — Keyboard.vhd (PS/2 Port 1)
- Decodes standard PS/2 protocol: 11-bit frames (start, 8 data LSB-first, odd parity, stop), sampled on falling clock edge.
- **Debounce:** 8-sample shift register on `ps2_clock`. Transition only accepted when 8 consecutive samples agree — removes ringing noise.
- **Break codes (0xF0):** `break_flag` latches; next byte is the key being released rather than pressed.
- **Extended codes (0xE0):** `extended_flag` latches; next byte is an extended scancode (arrow keys).
- **Scan codes mapped:**
  - Left arrow (0xE0 0x6B) → `left_key`
  - Right arrow (0xE0 0x74) → `right_key`
  - Spacebar (0x29) or Up arrow (0xE0 0x75) → `jump_key`
  - Down arrow (0xE0 0x72) → `dive_key`
- Level-held outputs — `Player.vhd` performs its own edge detection internally to prevent key repeat.

### Mouse — Mouse.vhd (PS/2 Port 2)
- Sends `0xF4` (enable data streaming) command on startup. Pulls PS/2 clock low for 60 µs first to inhibit the mouse's power-on self-test.
- Reads continuous 3-byte movement packets:
  - Byte 1: Button flags [left, right], movement sign/overflow bits
  - Byte 2: X delta (signed)
  - Byte 3: Y delta (signed)
- Integrates deltas into `cursor_x` [0–639] and `cursor_y` [0–479], clamped at edges.
- Outputs: `left_button`, `right_button`, `cursor_x`, `cursor_y`.

### Input Gating (Top_Level)
Four per-signal latches (`shift_left_gate_closed`, `shift_right_gate_closed`, `jump_gate_closed`, `dive_gate_closed`) implement a "must-release-once" gate. While the start screen is active, all gates are held closed. After the screen closes, each gate opens only once the corresponding input is physically released — prevents a mode-selection mouse click from immediately triggering a jump at the start of gameplay.

## 12. Start Screen — Start_Screen.vhd

### State Machine (3 States)
1. **title_screen:** Shows game title, group credits, "press any key to continue" prompt. Arms after 200 ms of no key held (guards against PS/2 glitches on power-on). Advances on any key press.
2. **mode_select:** Two hover buttons — "TRAINING" (left half, x < 320) and "SINGLE PLAYER" (right half, x ≥ 320). Button text scales from SCALE 1 to SCALE 2 when mouse cursor hovers over it. Left mouse click while hovering latches the mode selection and advances.
3. **game_running:** Kills all start screen output (RGB = "0000"). `startscreen_active = '0'`.

Quickstart bypass: `SW1 = '1'` + `KEY2 = '1'` skips directly to `game_running`. `SW0` selects mode (0 = Training, 1 = Single Player).

**Output:** `latched_mode` (locked until end screen acknowledges reset) and `startscreen_active`.

## 13. End Screen — End_Screen.vhd

Shown when `endscreen_active = '1'` from Game_Master.

**Layout:**
- "YOU" (SCALE 3, purple) at row 180
- "WIN" (green, SCALE 3) or "LOSE" (red, SCALE 3) at row 240 — determined by `endscreen_outcome`
- "CLICK ANYWHERE TO CONTINUE" (SCALE 1, muted purple) at row 320

Screen holds until any key is pressed (`any_key_pressed` rising edge while `endscreen_active = '1'`). On acknowledge: `screen_active` clears, Game_Master returns to `INIT_SCREEN`, SD card re-initializes (re-reads start sector).

## 14. HUD Overlay — HUD_Overlay.vhd

Displayed during gameplay and pause (not during start/end screens).

**Layout on 640×480 display:**
- Top-left: "LIVES" (green, SCALE 2) + life count digit (green, SCALE 4)
- Top-center: "SCORE" (yellow, SCALE 2) + 3 digits (white, SCALE 4)
- Top-right: "TIME" (cyan, SCALE 2) + MM:SS (cyan, SCALE 4)

**Score encoding:** 10-bit binary → 3 BCD digits via combinational priority chain:
```
if score >= 900: hundreds=9
elif score >= 800: hundreds=8
...
elif score >= 100: hundreds=1
else: hundreds=0 (blank with space character)
```
Same for tens digit. Ones = score mod 10. Each digit maps to character ROM index (48–57 for '0'–'9').

**Lives decoding:**
- Training mode (internal_lives is 2-bit up-counter from 0): "00"→3, "01"→2, "10"→1, "11"→0
- Normal mode: "10"→1, else 0

**Timer source:** `Game_Timer` (Section 15). Outputs BCD digits directly to HUD.

## 15. Game Timer — Game_Timer.vhd

Runs on CLOCK_50. Enabled only when `game_enable = '1'` (pauses when game is paused).

- Prescaler divides 50 MHz to 1 Hz tick: `CLOCK_HZ − 1 = 49,999,999` counts per second.
- BCD cascade counters: sec_ones (0–9), sec_tens (0–5), min_ones (0–9), min_tens (0–9).
- Caps at 99:59.
- Synchronous reset returns to 00:00.
- Outputs: `sec_ones`, `sec_tens`, `min_ones`, `min_tens` (4-bit BCD each) to HUD_Overlay.

## 16. Audio System

### SD Card — SD_Init.vhd + SPI_Master.vhd
- SPI communication at `CLOCK_50`. Initialization sequence: CMD0 (reset) → CMD8 (interface condition) → CMD55 + ACMD41 (initialization) → CMD16 (set 512-byte block size).
- Reads 512-byte sectors starting from `start_sector` address.
- Outputs bytes sequentially via `read_byte` with `byte_address` for random access within current sector.
- ~500 clock cycles per byte average read latency.

**Dual-buffer design:** Two 512-byte sector buffers (sector_buffer_a, sector_buffer_b, both altsyncram) allow ping-pong reading — one buffer fills from SD while the other is read by Audio_Playback, preventing audio gaps.

### Audio Playback — Audio_Playback.vhd
- Sample rate: 44,100 Hz. Prescaler: `SAMPLE_PERIOD_CYCLES = 50,000,000 / 44,100 ≈ 1,134 cycles`.
- Each tick: fetch 2 bytes from SD buffer (low byte address, then high byte address).
- **DAC output:**
  - `dac_high` (GPIO_0[19:12]) = 8 MSBs
  - `dac_low` (GPIO_0[11:4]) = 8 LSBs
  - Signed → unsigned conversion: MSB bit 7 inverted so silence = 0x80 (midpoint of DAC range)
- FSM: IDLE → fetch_low_byte_1 → fetch_low_byte_2 → fetch_high_byte_1 → fetch_high_byte_2 → IDLE

### Jukebox (Top_Level process)
`SW[6:4]` selects one of 5 music tracks. Each selection maps to a `start_sector` and `track_length`. Track change triggers a 1 ms reset pulse (50,000 cycles at 50 MHz) to safely abort any in-progress SD sector read before switching to the new track's start sector.

### Audio Gating
```
audio_gated_ready = audio_ready AND NOT(startscreen_fsm) AND NOT(endscreen_50_s2) AND NOT(SW(8)) AND SW(9)
```
Audio silenced during: start screen, end screen, SW8 (pause/mute), SW9 low (not held — acts as audio reset).

- **Logic (ALMs) usage is low (17%)** — the design is memory-bound, not logic-bound. Most complexity is in ROM lookups, not combinational logic.
- **RAM Blocks (61%)** dominate: 24 sprite ROMs (one per animation frame), 3× Object_ROM + Perspective_ROM (Moving_Object), Wave_ROM, Background_ROM, Character_ROM, SD card dual-buffer. This is by design — storing precomputed geometry and sprite data in block RAM is far more efficient than computing them on-the-fly.
- **DSP Blocks (76%)** — heavily used by Moving_Object (3 instances × multiple multipliers for perspective geometry calculations: lane offset × perspective scale, taper calculations, etc.). This is the design's most DSP-intensive module.
- **PLLs (1)** — single PLL for 50 MHz → 25 MHz pixel clock generation.

### Why DSP Usage is High
Each `Moving_Object` instance uses several multiplier operations for 3D perspective rendering:
- Lane position × perspective spread factor
- Taper × depth (top and side faces)
- View offset × perspective scale
Cyclone V maps these multiplications to 18×18 DSP blocks. With 3 instances, DSP usage escalates quickly. This is a deliberate trade-off: DSP blocks give exact results in 1–2 pipeline stages; LUT-based multipliers would add combinational depth and increase routing congestion.

### Timing Performance

All TNS (Total Negative Slack) = 0 on the slow model — **the design fully meets timing under worst-case conditions**.

| Clock | Period | Setup Slack (Slow 85°C) | Max Achievable Freq |
|---|---|---|---|
| CLOCK_50 | 20 ns | +11.229 ns | ~114 MHz |
| video_clock (25 MHz) | 40 ns | +24.468 ns | ~64 MHz |
| mouse_filter_clk | — | +83,325 ns | (very slow, ~Hz range) |

**One minor timing note:** Fast-model hold slack on the pixel clock is slightly negative (−0.013 ns / −0.079 ns at Fast 1100mV corners). This is a known Quartus phenomenon for tightly-timed video pipelines — fast-corner hold violations at −0.013 ns are below the margin of error of on-chip variation and do not affect silicon reliability at nominal operating conditions. The slow model (which reflects actual operating conditions) shows positive hold slack in all cases.

**Design runs comfortably at both 50 MHz and 25 MHz.** The limiting resource for higher frequencies would be the Moving_Object perspective pipeline and the HUD BCD decode chain (both resolved by inserted pipeline registers).

## 18. Key Design Decisions and Trade-offs

### 3D Perspective vs. Flat Side-Scroller
**Decision:** Implement full 3D perspective rendering with precomputed geometry tables.  
**Why:** Significantly more visually impressive. Demonstrates FPGA-specific design skills (ROM-based LUT arithmetic instead of floating-point, precomputed tables at synthesis time).  
**Trade-off:** Consumed 61% of block RAM and 76% of DSP blocks. Restricted available resources for other features. Justified by visual quality.

### Precomputed LUTs vs. Runtime Math
**Decision:** All perspective geometry, parabolic jump trajectory, and object dimensions stored as precomputed ROM tables.  
**Why:** Real-time multiplication/division in the pixel clock domain was the critical path. Jump_Offset_LUT specifically replaced a multiply+divide that limited pixel clock to ~45 MHz; LUT + register hit ~64 MHz. Object_ROM stores all 160 depth positions of object dimensions, computed once at synthesis.  
**Trade-off:** Extra M9K RAM blocks consumed. Zero runtime multiplier logic on the critical display path.

### Two Clock Domains
**Decision:** Separate CLOCK_50 (peripherals) from video_clock (display) with synchronizers.  
**Why:** PS/2 protocol requires stable CLOCK_50 sampling. VGA pixel clock must be exactly 25 MHz. Running everything on one clock would require either a compromise frequency or a very high CLOCK_50 with many dividers.  
**Trade-off:** Cross-domain synchronizers add 2-cycle latency on input signals (imperceptible to player). Requires careful identification of all cross-domain signals.

### GLOBAL Buffer on video_clock
**Decision:** Route `video_clock` through a GLOBAL buffer primitive in `Top_Level.vhd`.  
**Why:** ~1,000 loads on the video clock signal. Without GLOBAL buffer, clock skew causes pixel data to arrive at the wrong timing, corrupting the display completely.  
**Trade-off:** Consumes one of the GLOBAL routing resources (but the device has many).

### Pipeline Registers Inserted for Timing (Not Function)
Several pipeline registers exist purely to break long combinational paths:
- `Screen_Compositor` input + output registers (24 ns → 2×12 ns)
- `HUD_Overlay` BCD pipeline register (21 ns → 2×11 ns)
- `Player.vhd` local pixel coordinate registers (reduces VGA_Sync fanout by ~120)
- `Start_Screen.vhd` output register (prevents LUT sharing with End_Screen)
These add 1-cycle latency (40 ns at 25 MHz — invisible at 60 Hz frame rate).

### Input Gating
**Decision:** "Must-release-once" gate on all inputs when start screen closes.  
**Why:** Without this, a mouse click on "TRAINING" or a keyboard press on the start screen would be seen as a jump/shift in the first frame of gameplay.  
**Trade-off:** Adds logic complexity in Top_Level. The alternative (ignoring inputs for N cycles at game start) would be imprecise and might miss legitimate inputs.

### LFSR for Pseudo-Random Spawning
**Decision:** 8-bit Galois LFSR seeded with `0xB1`.  
**Why:** True random number generation is not practical in FPGA logic. LFSR is deterministic, synthesizable, and produces a sequence that appears random with a long period (255 unique states for 8-bit). Fixed seed means the sequence is repeatable — useful for testing.  
**Trade-off:** The game has the same obstacle sequence every playthrough (not truly random). Could be addressed by seeding LFSR from a timer value at game start — identified as a future improvement.

### Fractional Stepping for Object Speed
**Decision:** Objects advance by 1 or 2 pixels per vsync depending on which zone (0–5) they're in.  
**Why:** Objects must appear to accelerate as they approach (perspective effect). Linear distance increment would look wrong. Zone-based fractional stepping approximates the correct perspective acceleration without requiring division at runtime.  
**Trade-off:** Not a perfectly smooth acceleration curve — small discontinuities at zone boundaries. Not perceptible during gameplay.

## 20. Possible Future Improvements (for report discussion)

1. **LFSR seeded from timer:** Seed the LFSR with the value of the Game_Timer at the moment the game starts — gives a different obstacle sequence every playthrough without a true RNG.

2. **Obstacle generation:** Currently all three lanes can spawn independently (including combinations that are physically impossible to avoid). A collision-feasibility check on the Wave_ROM entries could guarantee every wave is solvable.

3. **DSP optimization:** Moving_Object uses many DSP blocks for perspective math. Some multiplications could be replaced with bit-shifts and additions (approximate perspective) to free DSP blocks and reduce power.

4. **Hold-violation at fast corner:** The −0.013 ns fast-model hold violation on the pixel clock is benign at operating conditions but could be resolved by inserting a small buffer or routing constraint on that path.

5. **Audio quality:** Current DAC is 8-bit on the high channel — 16-bit audio could be achieved with an external I2S DAC on GPIO, improving audio quality significantly.

6. **Score persistence:** Score and high score could be written back to SD card for persistence across power cycles.

7. **Difficulty randomization:** Obstacle spacing and types currently follow a fixed pseudo-random sequence. True difficulty scaling could adjust Wave_ROM dynamically (e.g., forbid type "000" empty entries at high levels).
